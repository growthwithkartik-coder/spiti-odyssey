# The Spiti Odyssey — Cinematic Edition
*New Year Mountain Party & Trek · event starts 27 December 2026 · trip price ₹1,60,000–₹2,30,000 per person*

A multi-page static website (17 routes + 404) generated by a tiny Node script — no framework, no `npm install`. This edition is a full visual redesign of the earlier site: a new expedition-journal identity, every supplied travel image placed in its named section, a new altitude-profile graphic system, much more motion, and expanded content on every page. Corrections: the hero attribution is gone (the footer carries **Operated and Managed by DemiGod House**), and the old ₹50,000–₹60,000 figure has been replaced everywhere by **₹1,60,000–₹2,30,000 per person**.

What changed and why: **`docs/CINEMATIC-EDITION.md`** (includes the image-placement table). Open questions for the operator: `docs/CONFIRMATIONS-NEEDED.md`.

---

## 1 · Run it

Needs **Node 18+**. Nothing to install.

```bash
npm run dev        # rebuild the pages, then serve at http://localhost:8080
npm start          # serve without rebuilding
npm run build      # regenerate public/ only
```

If port 8080 is busy, the server uses the next free port and prints it.

**Deploy:** upload the `public/` folder to any static host (Netlify, Vercel, Cloudflare Pages, S3, cPanel). Every route is a real folder with its own `index.html`. `404.html` assumes the site sits at the domain root. Opening files straight from disk mostly works, but the 3D route map needs a web server (it falls back to the SVG diagram otherwise).

## 2 · Edit content

- Facts (dates, contact, **prices**, stays, itinerary, enquiry options, open items): `src/data/trip.mjs`. Change `PRICING.package.from` / `.to` to update every price on the site and in the booking form.
- Images: `src/data/images.mjs` — Wikimedia route photographs plus the **supplied images** block (each records its original filename and intended section).
- Page layouts and copy: `src/pages/*.mjs` (shared cinematic blocks in `src/pages/_cinematic.mjs`, party sections in `src/pages/_party-sections.mjs`).
- Shared components and graphics (elevation profile, marquee, icons, price block, booking band): `tools/lib.mjs`. Layout, nav and footer: `tools/build.mjs`.

The build fails if a Wikimedia photograph is placed twice by accident, or if any supplied image is not placed anywhere.

## 3 · Design & motion

- `public/assets/css/expedition.css` — the Cinematic Edition design system (loaded after `odyssey.css` and `party.css`, which are kept).
- `public/assets/js/expedition.js` — page transitions, nav indicator, scroll-drawn elevation profiles, counters, marquee, parallax, magnetic buttons, tilt cards, drag-scroll, chapter indicator, itinerary timeline sync.
- `public/assets/js/site.js`, `party.js` — the original interactions (pinned scroll scenes, 3D terrain, lightbox, form, countdown, split text), kept.
- Vendor: GSAP 3.12.5 + ScrollTrigger, Three.js r160 (local files).
- Fonts are self-hosted in `public/assets/fonts/` (Instrument Serif, Archivo, IBM Plex Mono — SIL Open Font License, licences included).
- Everything respects `prefers-reduced-motion`; without JavaScript every page is still complete and readable.

## 4 · Images

- **Supplied images** (23 files from `updated_travel_images_v2 2.zip`): `public/assets/img/supplied/<name>-800|1600.(jpg|webp)`, served with `<picture>` (WebP first) and lazy loading below the fold.
- **Route photographs**: real photographs from Wikimedia Commons, credited in captions and on `/credits/`. 104 are bundled in `public/assets/img/`; the rest load from Wikimedia. To bundle them too: `npm run fetch-images && npm run build:local-images`. If a remote photo fails to load, a labelled illustration replaces it.

## 5 · Enquiries

The booking form validates every field and shows a review step before sending.
- **Default (`ENQUIRY.endpoint = null`):** it opens the visitor's email app with the enquiry filled in, addressed to `dev@demigodhouse.com`. The page tells the visitor plainly that the enquiry is only sent once they press Send in their email app.
- **With a backend:** deploy `server/` and set `ENQUIRY.endpoint` to `https://your-api/api/enquiry`. The form then POSTs JSON and shows success only when the server returns `{ ok: true }`, along with a reference number.

## 6 · Payments: not enabled (what's needed)

No payment is taken anywhere on the site, and the booking page says so. That is deliberate. The deposit is not confirmed and no merchant account was supplied. sevenchairs.in uses Razorpay with server-side order creation and verification; this project includes the same pattern, but **with no credentials of any kind**.

To switch it on:
1. Get the operator's own Razorpay account (KYC complete), with its **Key ID** and **Key Secret**.
2. Confirm the deposit per traveller. Set `PRICING.deposit` (and, per package, `PRICING.packageTotal`) in `trip.mjs`.
3. Deploy `server/server.mjs` (Node 18+) with the variables in `.env.example`: `PAYMENTS_ENABLED=true`, the two Razorpay keys, `CONFIRMED_DEPOSIT_PAISE`, `MERCHANT_NAME` and `ALLOWED_ORIGINS`.
4. In `trip.mjs`, set `PAYMENTS.enabled = true`, the two endpoint URLs, the **public** `keyId` and `merchantName`. Rebuild.
5. Add a pay button on the booking page that shows the exact amount and then calls `OdysseyPay.start({...})` from `public/assets/js/payments.js`. Test it in Razorpay test mode first.

How it stays safe:
- The server decides the amount, so the browser can't change it.
- The secret key never reaches the browser.
- The server checks the payment's signature with HMAC and then asks Razorpay to confirm the payment and amount.
- Duplicate verifications are recognised.
- Failed, cancelled and pending payments are each reported to the visitor.
- A booking is never marked as confirmed just because a button was pressed.
